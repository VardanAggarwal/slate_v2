Slate — how the engine works

A personal memory engine. The whole system hangs off one primitive — measure how new a piece of text is against memory's own spread, then decide what to do with it. The three flows below are just different (X, Y) plugged into that primitive.

The shared primitive · measure → decide → resolve_direction

Used by all three flows, three distinct stages. measure is a pure sensor (geometry). decide applies the compression bet (owned by consolidation, reversible). resolve_direction is a separate NLI stage that runs only on the AMBIGUOUS rows decide labelled — kept outside decide so decide stays pure & replayable.

measure(X, Y) — pure, no policy, no thresholds
① kNN — nearest neighbours of X inside corpus Y
② residual r = ‖X − reconstruct(X from neighbours)‖  → how new
③ z = (r − μ_region) / σ_region  → spread-RELATIVE, not raw cosine
④ anchor = nearest item + peer-similarity spread  → where it attaches
decide(measurement, calibration) — applies the bet
PREDICTED
z ≤ z_echo — reconstructs as tightly as the region itself. Store nothing, reinforce the anchor.
AMBIGUOUS
attached to an anchor but looser. Store + resolve DIRECTION via an NLI stance check (contradict / refine).
NOVEL
no anchor — open territory. Store as new.
↓  only the AMBIGUOUS rows continue
resolve_direction(fragment, anchor) — NLI stance, NOT inside decide
A discriminative NLI classifier (local CrossEncoder / HF zero-shot MNLI) reads the fragment against its anchor and returns a direction — geometry can't, since an encoder makes a paraphrase and its negation look identical.
contradict
sign −1 · held strongly, anchor flagged
refine
sign +1 · qualifies/extends the anchor
reinforce
sign +1 · restates (entailment)
★
Why this matters: "new" means the same thing in a dense cluster and a sparse one — novelty is judged against a region's own spread, never an absolute similarity cut. Geometry (knowable) is split from the compression bet (chosen). Direction is never geometry — an encoder can't tell a paraphrase from its negation — so it's deferred to a discriminative NLI stance classifier (not a generative LLM), run only on AMBIGUOUS.

Segment into fragments — plan_fragments() → fragment_representatives()

One surprise signal segments the note into variable-resolution fragments: mutually-predictable sentences fold together, surprising ones stay fine-grained. Each fragment is represented by its medoid sentence — a real sentence, selected not generated.

★
Critical value: the medoid reuses the encode-time vector → no second embedding pass, and provenance stays verbatim. Resolution follows surprise, so detail is kept exactly where it's informative.

W4–W6 · ASYNC · the primitive, batched

Route every fragment — route_fragments() → measure/decide → resolve_direction()

All fragments measured against memory in one batched pass (+ pushed-down baselines), plus a causal sibling check for intra-note dedup. An NLI stance classifier resolves DIRECTION for AMBIGUOUS fragments only — no generative LLM call here.

"embed via HF in prod" → PREDICTED echoes a stored fragment → reinforce anchor, store nothing "no torch on 1GB host" → NOVEL open territory → store "use OpenAI embeddings" → AMBIGUOUS → resolve_direction (NLI) → CONTRADICT held strong, flagged
★
Critical value: the only model call is the NLI stance check (local CrossEncoder, or HF zero-shot MNLI on the prod host) — cheap, discriminative, and only for genuinely ambiguous fragments. No generative LLM on the write path. A within-note echo collapses against a sibling, not memory — so a note repeating itself doesn't bloat the store.

W7–W8 · ASYNC · tag & save (no new decisions)

Tag and save — emit FRAGMENTED → apply_fragmented()

W7 — bookkeeping. Label two fragments: the centre (the note's main point — reconstructs best from memory) and the most-new one (highest surprise). Just flags; they change no decision.

W8 — save. All routing was already decided in W4–W6. This step just stores the result: write the decision to a log, then fill in the fragment rows and reinforce the matched anchors. Nothing new is decided here — but without it, nothing is saved.

★
Why write to a log first: the routing depended on the NLI call and on what memory looked like at that moment — neither can be reproduced later. Recording it once means the database can always be rebuilt from the log, and a repeat run can't create duplicate fragments.

Retrieve — assemble_context()

Two tools read your memory: recall — quick headlines, called often — and assemble_context — the full pull. They work the same way: your question lights up the notes nearest to it, then that light spreads along the links between ideas — but only toward ideas that add something new to what's already lit. The difference is only where they stop. recall stops the moment it knows where the answer lives and hands back a ranked list. assemble_context keeps going and quotes your own words from those spots.

✅
One engine, two stopping points. Both tools run the same navigator — resonance.activate() (core/resonance.py). recall stops at the activation field and renders headlines; assemble_context keeps going to quote verbatim spans (resonance_context). 100% local — no LLM on the read path.

The shared engine — activate() core/resonance.py

Both tools start here. Three ideas drive it — and each one carries a filter that tells a genuinely relevant idea apart from a popular one (a hub that lights up for every question).

① MANY ROADS, ONE PLACE
Split the question into parts — probes ("more productive" / "more isolated"). Each part lights the graph on its own. Wherever several parts point to the same idea, that idea is probably the answer, so it ranks higher (confluence).
② ONLY STEP SOMEWHERE NEW
When the light hops to a neighbouring idea, it only crosses if that idea adds something you don't already have. A near-repeat of what's lit is blocked. (Same "is this new?" test Write uses — residuals_against, now applied along the links.) This is what lets it reach a related idea two hops out.
③ FIND THE SPOT, THEN QUOTE
The walk only decides where the answer lives (the bright ideas). The answer itself is your own words, pulled verbatim from the notes behind those ideas. One walk gives both the overview and the exact source.
3 filters (without them, the walk just returns popular noise): don't let a hub shout — an idea linked to everything spreads less per link (÷degree0.5) don't add a repeat — the "is this new?" gate on every hop discount the generic — an idea wired to everything counts for less
YOUR QUESTION → split into parts (probes)
"Has remote work made me more productive, or more isolated?"  →  "more productive" · "more isolated"

assemble_context continues · quote — resonance_recall() → resonance_context()

Take the brightest ideas → find the notes behind them → quote them verbatim, in three layers: a short overview, a deep read of the top note, and one line each from the rest.

1 OVERVIEW

The brightest handful of concepts give a one-line summary + their top member claims — the at-a-glance picture a "what do I think about X?" question needs. The walk (not raw similarity) picks which concepts. Capped at ~35% of the budget.

concept · "Remote work"

2 THE TOP NOTE, IN DEPTH

Read the single brightest note closely (more lines from it) — "find the right note, then actually read it." It also keeps that note's standout lines even if they don't match the question word-for-word — the nuance a plain keyword match would miss.

deep-read → kept

Every other bright note gives one line → coverage across many notes. The budget reserves space for this breadth first, then hands the leftover to the deep read — so a narrow question funds depth, a wide one keeps coverage. No need to guess which kind it is.

How the quoted lines get picked and ordered

All the candidate lines (overview + deep read + breadth) go through one picker, weighted by how bright their idea was:

start from the question itself.

R5 / R6 repeatedly add the line that brings the most new information on top of what's chosen so far. A line that just restates one already picked adds nothing — so duplicates drop out for free.

stop once new lines stop adding much (ASSEMBLE_GAIN_FLOOR=0.20, max 24 lines) — "enough to answer."

R8 learn record which lines were used vs skipped, so consolidation can later demote notes that keep surfacing but never get used (signals=True in prod).

recall() — the same walk, stopped early

recall runs the exact navigate step above (resonance.activate, core/recall.py). Instead of quoting, it scores the brightest ideas and returns them as headlines. Its why-now tags come from two places — how an idea was reached, and what's recorded on it:

From the walk: 2-hop — reached by a hop, not a direct match → a non-obvious connection 🌉 bridge — the idea sits on a non-obvious cross-topic link
From the note's own record: 🔁 recurring — you've come back to it often 🕰️ dormant — not touched in a while, now resurfacing ⚖️ contested — you later wrote something that disagrees

Data model — what's saved where

Four layers, one rule: episodes are the immutable truth; the event log is the backbone; everything semantic is a derived view that rebuild() can re-create from episodes + events; config/caches sit outside and survive rebuild. (SQLite + sqlite-vec; every table is partitioned by user_id.)

SAVE written by save_note CONSOLIDATE written nightly RETRIEVE written on lookup IMMUTABLE insert-only, never updated
